# System and reliability brief

RunSense coordinates a training week around a runner's history and guide constraints. The implementation uses FastAPI, a plain accessible web frontend, Pydantic validation and SQLite for non-Strava demo/Sheets runs. An official Strava MCP source now provides a separate personal preview path with in-memory retention only. No credentials were available during implementation; the delivered demo uses synthetic history and local simulations. Real adapters have HTTP mock tests, not authenticated live service evidence.

The planning and logistics layer now runs on LangChain's `ChatAnthropic` rather than a hand-rolled HTTP tool loop. The environment contract, the six-request budget, the read-before-propose gate and the independent validation gate are unchanged and still tested. SQLite now carries typed SQLAlchemy tables — athletes, activities, plan weeks, sessions, alerts and tool traces — beside the original blob rows rather than in place of them, giving a queryable cross-run view without altering what the API, the web dashboard or the evaluation harness read. Spoken cues and SMS notices are genuinely wired to ElevenLabs and Twilio and are optional: with credentials absent they return an explicit marker instead of reporting a delivery that did not occur. Obstacle triage now has real, unit-tested decision logic, but no computer-vision measurement. A mobile app scaffold exists and has never been run.

## Decision and execution boundaries

The planning input is an independently athlete-authored Google Sheets log. A deterministic planner or optional bounded Claude tool loop proposes seven days. Independent rules reject inconsistent dates or distances, excessive volume, consecutive hard days, invented guide confirmations, and long spoken summaries. Track sessions count as outdoors. Live mode assumes no guide confirmed until an actual RSVP workflow exists, so it schedules indoor sessions only.

The server stores a validated preview. The live executor requires authenticated approval of that saved run. It revalidates before writing. Calendar events have stable athlete/date IDs, private ownership markers, and read-back checks. Notion stores the plan and rationale under a stable Plan ID. All external actions occur server-side; credentials stay in environment variables. Calendar invitations and notifications are not sent by this prototype.

Two optional delivery channels sit outside that write path. Synthesized speech is cached on disk under a hash of text, voice and model, so re-speaking an identical cue reuses the bytes instead of re-billing the provider, and a cached clip is streamed back by ID. The guide-cancellation adaptation sends one SMS reschedule notice when a destination number and Twilio credentials are configured; otherwise the trace records a skipped step naming what to set. SMS sends are not retried, because the provider offers no idempotency key and a retry could duplicate a message. Neither channel can block or invalidate a plan.

## Evidence available

- An executable 16-scenario synthetic evaluation covers ten athlete constraints, repeat execution, guide cancellation, missed-session adaptation, an injected simulated 503 and rejection cases.
- Pytest exercises production rules, persistent action identity, saved-run replay, API access controls and HTTP provider contracts.
- Baseline verification before the MCP addition on 13 September 2026: **42 pytest tests passed**, **16/16 evaluation scenarios passed**, JavaScript syntax check passed, and the dashboard rendered without horizontal overflow at a 390-pixel viewport. Two dependency deprecation warnings remain; no test failures.
- After the MCP implementation: 80 pytest tests passed, including MCP session/protocol negotiation, streamed SSE completion, bounded responses, discovery, 401/403 handling, explicit read-only tool gating, token-rotation reconnect, field mapping, sport filtering, deduplication, memory-only previews, expiry, same-origin access and an explicit LAN-host allowlist for phone testing.
- Current verification on 13 September 2026: **206 pytest tests passed**, one dependency deprecation warning, no failures; mobile TypeScript compilation and **4 Jest triage tests** also pass. The added coverage includes the coach/change-request routes, stereo earcon asset validation, TypeScript triage behavior, and the native integration seams.
- Every external provider in the test suite is driven through `httpx.MockTransport`. That includes Anthropic, ElevenLabs and Twilio: the delivery code paths are real, but no test in this repository has issued a network call to any of them. Mock-transport coverage is a contract check, not live-service evidence.
- Trace and alert recording into the typed tables is best-effort by design. Failures are reported, never raised, and this is tested by injecting a locked database and a missing table: an otherwise valid plan, commit or alert stream must not be voided by a bookkeeping failure.
- Obstacle triage logic — zone thirds, NEAR/MID/FAR buckets, the tier table, the three-frame debounce, the fifteen-frame re-announcement window and DANGER pre-emption — is verified against ten procedurally generated detection sequences. `runsense.perception_eval` reports `"status": "triage_logic_tested"`. That string describes the decision logic and nothing else; it is not an accuracy result and must not be quoted as one.
- The detector wrapper has never been executed. There is no camera, no labelled footage and no on-device run in this environment, and the optional `ultralytics`/`opencv-python-headless` dependencies are imported lazily so the rest of the system stays importable without them.
- The mobile app passes `npx tsc --noEmit` and four Jest triage tests. Its VisionCamera/TFLite frame processor, OS speech recognition, and native audio wiring have never run on a device, simulator, emulator or Expo Go. The YOLO11n export confirmed `(1, 84, 8400)` but LiteRT conversion failed on this Python 3.14/Torch environment, so no model asset is bundled.
- The dashboard exposes step status, attempt number, measured local duration where available, and explicit descriptions of simulated calls. A zero duration is uninstrumented/sub-millisecond bookkeeping, not a device performance claim.
- Browser speech is user-triggered. Computer vision recall, zone accuracy, false alarms and end-to-end playback latency remain unmeasured. The PDF's under-400 ms capture-to-audio target is therefore still unsubstantiated and is not reported anywhere in this build.

Run `.venv/bin/python -m pytest -q`, `.venv/bin/python -m runsense.evaluation` and `.venv/bin/python -m runsense.perception_eval` from the repository. No test sends a real invitation, writes to a real app, or calls a model, speech or SMS provider.

## Failure behavior and limitations

Transient HTTP status failures have bounded provider retries. Calendar ID conflicts require ownership verification before update. Notion queries by Plan ID and must reconcile ambiguous creates without blindly replaying POST. Cross-app writes are not transactional: earlier successful writes remain if a later step fails. Traces persist incremental progress; retries must use the same saved run. One in-process lock serializes live actions. Run a single worker; multi-process/restart guarantees need a durable execution lease and stronger provider reconciliation.

The demo is a single-athlete local prototype. OAuth bootstrap/refresh, live guide consent/RSVP, preferences, cancellation/removal of old calendar events, native camera/model execution, native audio, and accessibility testing with blind runners remain open. Ask coach and change-request routes now exist, but the optional LLM needs an authenticated smoke test; mock-transport tests alone do not demonstrate live AI behavior. The same applies to the speech and SMS channels.

The perception work is a decision layer without a measured perceiver. Running the triage fixtures proves the alert rules behave as specified on hand-built inputs; it says nothing about whether a detector would find the obstacle, place it in the right zone, avoid false alarms, or complete the loop from camera to audio in time. Those four questions need labelled clips, a phone and an instrumented end-to-end timer, none of which exist here. The mobile scaffold is likewise unproven as software: a type check is not a run, and nothing in it has been exercised by a blind runner or on real hardware.

The Strava source uses an externally authorized MCP bearer token and discovered activity tool, with explicit field mapping. It neither accepts a Strava REST token as an equivalent nor silently substitutes fixtures when access fails. Strava-derived history is never put in SQLite, Calendar or Notion by this implementation.
