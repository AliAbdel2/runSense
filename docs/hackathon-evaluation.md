# RunSense hackathon evaluation

Prepared 13 September 2026 from the supplied technical plan and the published event page. This is a submission-readiness review, not a claimed rubric score.

## Assessment

RunSense has a strong, specific user problem: a blind or low-vision runner needs a manageable training week and dependable guide logistics, with spoken output. The most defensible hackathon story is the closed loop from an athlete-authored training log to a constrained plan, Calendar commitments, and a Notion journal. The current runnable artifact is a deterministic planning demo with an optional Claude path. It is a credible foundation for the two-minute submission, but it is not yet evidence of live app connectivity or real-time obstacle perception.

The implementation should make three states visible in the UI and brief:

| State | What can be said | Evidence required |
| --- | --- | --- |
| Working now | Local plan generation, constraints, trace, and reliability checks run end to end. | Reproducible command, screenshot or recording, trace and check output. |
| Connected and verified | A user-authorized Google Sheets read, Google Calendar write, or Notion write completed during rehearsal. | Timestamped response or event/page link with secrets removed; retry/idempotency trace. |
| Built but unproven | Obstacle triage logic, ElevenLabs/Twilio delivery, and a mobile scaffold now exist in the repository, each short of the evidence that would let it be demonstrated as working. | Name the exact check that passed — triage logic against synthetic fixtures, provider clients against mock transports, the mobile app against a type check — and the check that does not exist. |
| Planned | Real obstacle detection on footage, on-device inference, and any verified spoken or SMS delivery are still next steps. | A measurement against labelled clips or a real provider call; no live claim from code alone. |

The middle row is new and is the easiest row to overstate, so state it in three parts. The alert decision logic in `runsense/triage.py` is genuine and unit tested — zone, distance bucket, tier, debounce, re-announcement and DANGER pre-emption — and `runsense.perception_eval` exercises it over ten procedurally generated detection sequences. The detector wrapper around it has never been run: there is no camera, no labelled footage and no on-device execution in this environment. ElevenLabs speech and Twilio SMS are really called by the delivery code and are cached and traced, but every test drives them through a mock transport, as the Sheets, Calendar and Notion adapters are; no request has left this repository, and the same is true of the Claude path after its move to LangChain. The `mobile/` scaffold has passed `npx tsc --noEmit` and nothing else: it has never run on a device, a simulator or Expo Go, and its voice capture and camera perception are stubs. Describe each of these as implemented-and-logic-tested, never as working, and do not let a demo imply a runner has heard an alert.

## Event fit and corrections to the PDF

The official event page says the brief is one useful, multi-step AI agent connected to at least three external apps, with a working project or repository, a two-minute demo, and a short system/reliability brief. Teams are one to four people. The published build window is 9:30 AM–4:00 PM Pacific (6.5 hours), followed by judging; the PDF's “48-hour build” and five-minute demo are planning assumptions and must not drive the submission. The published weights are technical execution 30%, reliability and evaluation 25%, usefulness 20%, originality 15%, and demo clarity 10%. [Official hackathon brief and schedule](https://multiappagenthackathon.com/)

The implementation now has a narrow, personal alternative to the Sheets activity source: an optional direct client for Strava's official, Strava-controlled MCP at `https://mcp.strava.com/mcp`. It uses Streamable HTTP discovery and tool calls, maps only the authorized operator's activity history into a bounded in-memory preview, and feeds the existing deterministic planner or optional Claude path. It does not use the Strava REST API, a third-party MCP wrapper, or a REST fallback. The preview is read-only, expires within one hour, is not persisted to SQLite or Notion, and cannot be committed or externally exported while policy review is pending. [Strava MCP setup and lifecycle](strava-mcp.md)

This is not a broad Strava ban. Strava's API Policy §3.5 permits a subscriber's personal use of the official Strava MCP with their own data, while excluding commercial or third-party access outside that personal use. Sections 5.3 and 5.4 continue to restrict ordinary Strava API data and derivatives in AI operation, grounding, evaluation, analytics, and retrieval. RunSense therefore supports either an independently athlete-authored Sheets log or the personal `strava_mcp` preview for one local account; it must not present the latter as a multi-user integration or as permission to export Strava data. [Strava API Policy (2026)](https://www.strava.com/legal/api_policy) · [Strava MCP connector](https://support.strava.com/en-us/articles/15401531-what-is-the-strava-mcp-connector)

Use a small, independently athlete-authored Google Sheets log for the ordinary three-app submission path. It should contain only the fields the athlete chose to provide (for example date, distance, perceived effort, and guide availability), and should be read only for that athlete's plan. A personal Strava MCP preview can be used as an alternate local source for the same operator, but it does not add a fourth app or authorize Calendar/Notion writes. The three app path remains Google Sheets → Google Calendar → Notion. Treat ElevenLabs as optional audio delivery, not as one of the three apps unless the organizer confirms that a voice API qualifies and the integration is live. Never describe local fixtures, a mocked adapter, or a Strava handshake without eligible history as a connected app.

Several landscape claims also need narrower wording. Google describes a Running Guide agent for blind and low-vision runners in May 2026; its published description covers planning with weather, Maps, and workout goals and a Coach experience. That makes “zero coaching/logistics” and “first” claims unsafe. Google also open-sourced Project Guideline, an earlier computer-vision accessibility platform. Describe RunSense as a focused integration and accessibility-constraint contribution that complements those efforts, rather than as the first system or as an empty category. [Google Running Guide agent](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/running-guide-agent/) · [Project Guideline](https://research.google/blog/open-sourcing-project-guideline-a-platform-for-computer-vision-accessibility-technology/)

## Evidence plan by judging weight

| Criterion | Submission evidence | Release gate |
| --- | --- | --- |
| Technical execution (30%) | A trace showing Sheets or the personal Strava MCP preview read, plan/validation, Calendar write, and Notion journal write; typed tool inputs/outputs; deterministic idempotency key; optional Claude response shown as a replaceable reasoning layer. | Three real, user-authorized app calls succeed in one rehearsal, or the brief explicitly labels the path as pending and shows the local equivalent. A Strava MCP handshake alone is not activity-history evidence. |
| Reliability & evaluation (25%) | Constraint checks over fixed athlete fixtures; a forced Calendar failure/retry; duplicate-plan replay proving one event; persisted trace with errors and latency. | Checks are repeatable and fail on a violated hard rule; a retry does not duplicate a side effect. |
| Usefulness (20%) | One persona and one concrete week: guide confirmation changes the venue; every result has a spoken summary and reason. | No outdoor session is scheduled without a confirmed guide. |
| Originality (15%) | Accessibility constraints are decisions in the planner, not a decorative paragraph; Sheets, Calendar, and Notion close a personal workflow, with an official personal Strava MCP source available where the operator is eligible. | Keep claims comparative and sourced; call the product an assistive planning layer, not a guide replacement. Do not imply a multi-user Strava service. |
| Demo clarity (10%) | A two-minute screen recording or live run with one scenario, one change, one trace, and one limitation. | Rehearse to 1:45–1:55; keep a local fallback if credentials or network fail. |

## Safety and evidence boundaries

The 10% weekly-volume rule is a conservative product heuristic, not a medical safety guarantee. A randomized trial in novice runners found no injury-prevention effect from a 10% rule-based graded program. Keep the rule as an inspectable planning constraint and tell the user to adjust or stop with a clinician or coach when appropriate; do not promise injury prevention. [Buist et al., PubMed PMID 17940147](https://pubmed.ncbi.nlm.nih.gov/17940147/)

The PDF's “track” exemption should not be presented as proof that an unguided outdoor run is safe. The implementation requires a confirmed guide for every outdoor session. The fixed demo profile assumes treadmill access; athlete preferences must be captured before a pilot. Live guide RSVP handling is deferred, so all live-mode workouts remain indoors. RunSense does not replace a guide, navigation aid, or emergency service.

Do not report the PDF's “under 400 ms” perception target until a capture-to-audio measurement exists. A timer that starts after capture, inference, or queueing excludes camera capture and playback and cannot substantiate end-to-end latency. If perception is not implemented in this build, show it in the backlog and remove recall, zone accuracy, and latency numbers from the demo.

This instruction did not lapse when the triage logic landed, and the harness output is the specific thing most likely to be misread as retiring it. `runsense.perception_eval` reports `"status": "triage_logic_tested"` with ten of ten fixtures passing. Those ten are hand-placed bounding boxes generated in Python, so the number counts decision cases, not clips, and the status names the layer that was tested rather than a result. It is not a recall figure, a zone-accuracy figure, a false-alert rate or a latency measurement, and quoting it beside the PDF's targets — or letting a slide place it where an accuracy number would go — would misrepresent it. The four unmeasured quantities the harness itself lists stay in the backlog until labelled clips, a phone and an end-to-end timer produce them.

## Prioritized build and rehearsal backlog

1. Keep the deterministic local flow green: fixture → constraints → plan → trace → evaluation panel.
2. Verify Google Sheets read, Google Calendar insert/update, and Notion page append with a dedicated test account; if demonstrating the personal Strava MCP alternative, verify OAuth, `tools/list`, the configured activity tool, row validation, and the one-hour memory expiry. Redact tokens and personal data from traces.
3. Add idempotency and retry evidence for each write, including one deliberate transient failure.
4. Make connection status and “demo/local” labels impossible to miss; expose an honest `No apps connected` fallback. A Strava MCP connection check must show the tools actually discovered and must not claim historical activity eligibility from protocol connectivity alone.
5. Record the two-minute demo and a backup with local fixtures. Add an audio clip only if it is already tested; do not make TTS a release gate.
6. Perception now sits behind its own interface, with the alert decision logic separated from the detector and tested independently. The remaining half of this item is unchanged: evaluate it on labelled clips, measure capture-to-audio latency on a phone, and keep it out of anything the planning demo implies.
7. The mobile scaffold's next gate is running it — on a simulator first, then a device — before any screen appears in a recording. A type check is not a demo.

## Unknowns to resolve before submitting

The event page says official rules will be available before registration. Confirm whether pre-event work is eligible, whether each of the three apps must be live during judging, whether Google Sheets/Calendar/Notion satisfy the app definition, whether a personal first-party Strava MCP preview can be shown without counting as an additional app, and what evidence the judges expect for authorization and reliability. Until those answers are published, preserve the local fallback and label all unverified integrations as pending. No autonomous Strava or Claude sign-in has been performed, and the live MCP path remains unverified without an independently authorized token.
